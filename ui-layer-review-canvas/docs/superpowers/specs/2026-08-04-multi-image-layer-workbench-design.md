# Imvia Layer 多图片独立拆分设计

日期：2026-08-04
状态：总体方案已确认，待用户审阅书面设计
范围：`ui-layer-review-canvas` 的画布总览、框选拆分、任务排队、结果回流和刷新恢复

## 1. 背景与问题

当前工作台的数据模型只允许一张活动原图。`sourceImage`、`sourceName`、`sourceSize`、`nodes[]`、`marks[]` 和画布位置都是单份全局状态；加载新图时会清空图层、标注、结果关联和画布布局。

“画布总览”目前只是这张单图的原图、拆分项和结果节点视图，并不具备多图片项目语义。直接在现有画布上增加多个原图节点会造成以下风险：

- 图层仍引用全局原图，切换图片后框选预览会串图。
- 同文件名、同尺寸图片可能被现有任务匹配逻辑误判为同一来源。
- 新图载入会清空其他图片的任务和结果。
- 队列任务回流时依赖当前活动图片，切换图片可能让结果落到错误节点。
- 页面刷新后无法完整恢复多张原图和各自的编辑状态。

本设计将工作台升级为一个包含多张独立图片的本地项目。无限画布统一管理所有图片，框选拆分仍然一次只编辑一张图片，任务继续在当前 Codex 会话中可见、串行执行。

## 2. 目标与成功标准

### 2.1 目标

- 一个工作台项目可以上传、展示和管理多张原图。
- 每张图片拥有独立的图层、框选、标注、任务、结果和画布布局。
- 单击原图只选中节点；双击原图进入该图的框选拆分。
- 当前 Codex 会话正在执行任务时，其他图片的拆分任务可以继续进入同一可见队列。
- 队列仍一次发送和执行一个任务，不引入隐藏后台拆分或并行 Codex 任务。
- 切换图片、刷新页面或调整其他图片，不影响已提交任务的不可变输入快照。
- 结果严格通过项目、图片、图层和任务身份回流，不通过文件名或尺寸猜测归属。
- 现有单图片项目能够无损迁移为只含一张图片的多图片项目。

### 2.2 成功标准

以下场景必须通过：

1. 同时载入两张同文件名、同尺寸但内容不同的图片。
2. 分别创建图层、标注边界并提交拆分。
3. 第一张图执行期间，第二张图的任务进入排队。
4. 在两张图之间反复切换并刷新工作台。
5. 两个任务完成后，PNG、状态和耗时分别回到正确图片的正确图层。
6. 删除或重新分析其中一张图片，不改变另一张图片的任何状态。

### 2.3 非目标

- 第一阶段不支持跨图片连接、合成或共享图层。
- 第一阶段不支持同时打开多个框选编辑器。
- 不创建独立后台 Codex 任务，也不并行执行多条当前会话拆分。
- 不改变现有 ImageGen、RMBG、透明 PNG、尺寸和终态报告合同。
- 不重写无限画布渲染引擎，不引入新的远程数据库或云端服务。

## 3. 已确认的产品决策

### 3.1 画布统一管理，框选单图编辑

画布总览展示项目中的全部原图节点及其图层树。单击原图用于选择、拖动、编组和删除；双击原图进入框选拆分，并将该图片设为 `activeImageId`。

框选拆分继续沿用当前单图界面。左侧图层列表、中央框选预览、右侧需求和结果只读取活动图片的数据。返回画布时保留之前的缩放、平移和节点位置。

### 3.2 图片完全隔离

每张图片是独立 `ImageDocument`。图片之间不得共享图层 ID、标注、自动分析状态、任务状态、结果位置或框选编辑状态。

跨图片复制或连接属于后续独立功能，不在本设计中隐式支持。

### 3.3 当前会话串行队列

所有拆分任务仍通过当前 Codex 会话发送并可见执行。工作台可以在活动任务存在时继续接收其他图片的新任务，但会话监听一次只领取队首任务。

活动任务终态确认后，监听自动发送下一条排队任务。切换当前活动图片不改变队列顺序，也不停止监听。

## 4. 方案选择

### 4.1 采用：多图片项目模型

建立 `ProjectState` 和 `ImageDocument` 两级状态。画布从全部图片派生节点，框选拆分从 `activeImageId` 派生活动图片状态。

优点：

- 图片边界明确，任务和结果可以可靠隔离。
- 可以完整利用无限画布管理多个拆分树。
- 保持现有单图框选界面和当前会话执行方式。
- 支持增量迁移，不需要一次重写全部拆分逻辑。

### 4.2 不采用：切换图片时保存和恢复全局快照

该方案改动较小，但仍存在全局状态窗口。异步分析、轮询回流和正在执行的事件可能在切换期间写入错误快照，难以证明不会串图。

### 4.3 不采用：每张图片独立页面或浏览器标签

隔离最简单，但失去统一画布、统一队列和项目级管理价值，并重新引入多标签页监听和生命周期问题。

## 5. 领域模型

### 5.1 ProjectState

项目是工作台的顶级持久化对象：

```text
ProjectState
  version
  projectId
  revision
  activeImageId
  imageOrder[]
  imagesById{}
  canvasViewport
  canvasGroups[]
  createdAt
  updatedAt
```

- `projectId`：工作台项目的稳定随机 ID。
- `revision`：项目状态的单调递增版本，防止旧页面覆盖新状态。
- `activeImageId`：当前框选拆分正在编辑的图片。
- `imageOrder`：画布和图片切换器的稳定顺序。
- `imagesById`：按图片 ID 存储完整图片文档。
- `canvasViewport`：多图画布共享的平移与缩放。
- `canvasGroups`：只保存画布视觉编组，不改变图片归属。

### 5.2 ImageDocument

```text
ImageDocument
  imageId
  source
    name
    localUrl
    localPath
    width
    height
    fingerprint
    revision
  layers[]
  marks[]
  selectedLayerId
  analysisState
  layout
    sourceNodePosition
    resultNodePositions{}
    manualResultNodes[]
    manualEdges[]
    hiddenResultKeys[]
  createdAt
  updatedAt
```

`source.fingerprint` 使用原图文件内容的 SHA-256，而不是文件名、尺寸或浏览器对象 URL。`source.revision` 在原图被允许替换时递增，使旧任务快照无法写回新版本。

### 5.3 全局身份

所有可回流对象必须使用稳定身份：

```text
projectId
imageId
sourceFingerprint
sourceRevision
layerId
jobId
```

画布 Key 使用命名空间：

```text
source:<imageId>
layer:<imageId>:<layerId>
result:<imageId>:<layerId>:<jobId>
manual-result:<imageId>:<manualResultId>
```

`layerId` 在整个项目内唯一。即使未来允许复制图层，也必须生成新 ID，不能复用来源图层 ID。

## 6. 前端状态边界

### 6.1 状态访问

当前大量组件直接读取单份 `sourceImage`、`nodes` 和 `marks`。迁移后统一从以下派生值读取：

```text
activeImage = project.imagesById[project.activeImageId]
activeLayers = activeImage.layers
activeMarks = activeImage.marks
```

框选模式只能通过带 `imageId` 的项目操作修改状态，例如：

```text
addImage
removeImage
activateImage
updateImageSource
setImageLayers
updateLayer
setImageMarks
updateImageLayout
```

组件不得保留一套可绕开 `imageId` 的全局写入接口。

### 6.2 图片载入

现有 `loadSourceFile()` 会清空全局状态。它需要拆分为：

- `createImageDocument(file)`：读取、持久化原图并生成图片身份。
- `analyzeImage(imageId)`：只更新该图片的分析状态和候选图层。
- `placeImageTree(imageId)`：在画布空白区域放置原图及默认图层节点。

载入新图不得执行全局 `setJobs([])`、清空其他图片节点或重置共享画布。

### 6.3 原图替换

替换只作用于当前图片：

- 存在非终态任务时禁止替换，并提示先取消或等待完成。
- 没有非终态任务时允许替换，递增 `sourceRevision`。
- 替换后清空该图片的图层、标注和未固定结果，不影响其他图片。
- 历史已完成任务保留在任务记录中，但不再挂到新版本图片树。

## 7. 画布交互设计

### 7.1 多图节点树

每张图片在画布上拥有独立树：

```text
原图 A -> 图层 A1 -> 结果 A1
       -> 图层 A2 -> 结果 A2

原图 B -> 图层 B1 -> 结果 B1
       -> 图层 B2 -> 结果 B2
```

自动布局只计算新图片树的空白位置，不重新排布用户已经移动的节点。首个原图沿用当前默认位置；后续原图按项目画布空闲区域横向或纵向排布。

### 7.2 选择与进入编辑

- 单击原图：选择节点，不改变模式。
- 双击原图：设置 `activeImageId`，切换到框选拆分并选中该图上次编辑的图层。
- 单击图层节点：选中节点并显示该图片的画布检查器。
- 双击图层节点或点击编辑按钮：设置对应 `activeImageId` 和 `selectedLayerId`，进入框选拆分。
- 返回画布：保留多图画布视口。

### 7.3 删除

- 删除原图节点等同于删除整个 `ImageDocument`。
- 有排队任务时，必须先取消该图片的排队任务。
- 有执行中任务时禁止删除，等待任务终态后再操作。
- 删除一张图不删除其他图片、共享画布视口或其他图片的任务记录。
- 删除当前活动图片后，选择 `imageOrder` 中的下一张；项目为空时回到上传入口。

## 8. 任务与计划合同

### 8.1 提交快照

每个任务提交时冻结完整输入：

```text
project_id
image_id
source_fingerprint
source_revision
source.local_path
source.canvas
layers[]
mask_annotations[]
execution_mode
execution_route_hint
output_directory
submitted_at
```

任务目录继续保持唯一。源图和框选预览在任务建立时复制或锁定到任务目录，之后编辑项目状态不能改变已提交任务。

### 8.2 队列

队列是当前会话级串行队列，不按活动图片拆分为多个执行通道：

1. 任意图片可以提交任务。
2. 新任务记录为 `queued` 或现有等价等待状态。
3. 当前有效会话监听只领取最早且可执行的任务。
4. 当前任务终态确认后领取下一项。
5. 图片切换、画布选择和页面视口变化不影响队列。

任务卡片和工作台进度必须同时显示图片名与图层名，避免多图情况下只显示“UI 组件 1”而无法辨认来源。

### 8.3 结果回流

结果路由必须依次验证：

1. `jobId` 属于当前项目。
2. `imageId` 存在。
3. `sourceFingerprint` 和 `sourceRevision` 与任务快照一致。
4. `layerId` 属于该任务快照。
5. 执行报告和 PNG 验收通过。

任一步不匹配都拒绝挂载结果，并记录明确失败原因。禁止退回到文件名、图片尺寸、当前活动图片或节点顺序猜测。

## 9. 持久化与恢复

### 9.1 权威存储

本地工作台服务保存项目状态和原图文件：

```text
output/projects/<projectId>/project.json
output/projects/<projectId>/sources/<imageId>/source.png
```

任务仍保存在现有唯一任务目录，不与项目源图目录混写。

`project.json` 通过临时文件加原子替换写入。浏览器 `localStorage` 只保存最近项目 ID 和少量视图偏好，不保存大图 Base64，也不作为项目权威数据源。

### 9.2 刷新恢复

页面启动时：

1. 读取最近项目 ID。
2. 从本地服务加载 `project.json`。
3. 恢复图片顺序、节点位置、活动图片和画布视口。
4. 加载每张图片的任务摘要和可用结果。
5. 对非终态任务恢复轮询和队列显示。

项目 `revision` 用于拒绝明显过期的页面写入。单用户正常流程不增加复杂实时协同；多标签页发生冲突时，旧页面重新载入最新项目状态后再操作。

### 9.3 单图迁移

旧状态存在原图时，启动迁移生成一个 `ImageDocument`：

- 旧原图成为首张图片。
- 旧 `nodes[]`、`marks[]` 和布局迁入该图片。
- 旧任务只有在可以可靠匹配原图文件时才关联；无法可靠识别的历史任务保留为未归档记录，不猜测挂载。
- 迁移成功后写入 `version: 2`，不再使用旧全局结构。

### 9.4 与现有工作台生命周期兼容

多图片持久化不改变已经确认的页面租约和关闭语义：

- 页面刷新、热更新或租约宽限期内重连，恢复项目、队列和结果轮询，不视为关闭。
- 最后一个页面超过租约宽限期仍未恢复时，继续执行现有关闭策略：未被模型确认的排队任务取消，已开始任务标记为遗弃。
- 再次打开工作台可以恢复多图片项目和正常完成的历史结果，但不能恢复已按生命周期规则取消或遗弃的任务。
- 项目持久化只保证图片和编辑状态不丢失，不延长会话监听或本地服务的生命周期。

## 10. 错误处理

- 单张图片分析失败：该图片显示失败和重试入口，其他图片继续工作。
- 原图文件缺失：图片树进入“原图不可用”，禁止新拆分但保留已完成结果。
- 指纹或版本不匹配：拒绝回流，显示“结果属于旧原图版本”。
- 持久化失败：本次操作不提交到内存终态，提示重试，避免界面成功但刷新丢失。
- 队列监听离线：任务保留在队列，图片切换不改变其状态。
- 图片删除与任务认领竞争：通过服务端串行锁保证取消或认领只有一方成功。
- 项目状态损坏：保留损坏文件副本并进入只读恢复提示，不自动覆盖。

## 11. 测试设计

### 11.1 单元测试

- 项目和图片操作只修改目标 `imageId`。
- 画布 Key 在不同图片之间不冲突。
- 结果路由拒绝错误项目、图片、指纹、版本和图层。
- 原图替换只递增目标图片版本并清理目标图片状态。
- 删除图片不会改变其他图片或任务。
- 旧单图状态可以迁移为 `version: 2`。

### 11.2 集成测试

- 两张同名同尺寸图片分别提交并正确回流。
- 图片 A 执行时，图片 B 排队；A 完成后 B 自动发送。
- 排队期间切换活动图片不改变任务归属和顺序。
- 刷新后恢复多图画布、活动图片、队列和已完成结果。
- 删除含排队任务的图片先取消任务，不能留下幽灵队列项。
- 图片有执行中任务时替换和删除被阻止。

### 11.3 浏览器交互测试

- 多文件上传后出现多个原图树。
- 单击只选择，双击进入对应框选拆分。
- 从框选模式返回后画布视口不跳变。
- 当前图片名称、图层列表和结果预览一致。
- 在两张图片之间往返时，框选位置和标注不互相污染。

### 11.4 回归测试

- 单张图片上传、分析、框选、提交、结果下载保持现有行为。
- 当前会话可见消息和确认链路保持不变。
- 现有任务生命周期、排队、取消、终态快速结束和 RMBG 路由测试继续通过。

## 12. 分阶段实施与回滚

### 阶段 1：项目模型和持久化

建立纯数据层、项目存储和单图迁移。界面仍只展示首张图。通过模型和迁移测试后才能进入下一阶段。

### 阶段 2：多原图画布

画布渲染多个原图树，完成命名空间 Key、独立布局、上传和删除。任务提交仍暂时限制为活动图片。

### 阶段 3：框选切换

实现双击进入、活动图片切换和按图片隔离的图层、标注及检查器。

### 阶段 4：多图队列和结果路由

给任务合同、会话卡片、队列和回流增加完整图片身份，移除文件名加尺寸的归属判断。

### 阶段 5：恢复与端到端验收

完成刷新恢复、冲突处理、同名同尺寸测试、迁移测试和浏览器交互验证。

每个阶段通过功能开关启用。回滚只关闭新多图入口，不修改已经完成任务的目录和报告；项目文件保留，重新启用后可继续恢复。

## 13. 完成定义

功能只有在以下条件全部满足时才算完成：

- 多图片之间不存在共享可变拆分状态。
- 结果归属不再依赖文件名或尺寸。
- 当前会话执行仍然可见且严格串行。
- 忙碌期间其他图片的新任务可以真实进入队列。
- 页面刷新后能够恢复多图项目和任务状态。
- 同名同尺寸双图片端到端测试通过。
- 全部既有测试、生产构建和实际浏览器交互验证通过。
